Visión general

¿Qué hace esta herramienta y cómo?

La herramienta es un motor de valoración automatizada de rentas para el mercado de CDMX. Dada una propiedad descrita por su código postal, coordenadas, m², recámaras y baños, consulta simultáneamente 4 fuentes de datos independientes, limpia y ajusta los precios históricos por inflación, y escribe el precio sugerido directamente en Google Sheets.

Técnicamente es un pipeline de datos Python que corre en local. No es un servicio web ni una API — se ejecuta manualmente cuando hay filas nuevas en la hoja de cálculo.

Las 4 fuentes de datos

SQL / Redshift

Qué contiene: Histórico de web scraping de portales de renta de CDMX, almacenado en Redshift (Panoply). Últimos 40 meses.
Qué mide: Precio de anuncio al momento del scraping.
Fortaleza: Volumen de datos alto.
Debilidad: No confirma que el inmueble se rentó realmente.

Homie histórico

Qué contiene: Contratos de renta reales gestionados por Homie (status: started, finished, finished_early).
Qué mide: Precio de renta cerrado y pagado.
Fortaleza: Es el único dato de precio real de cierre.
Debilidad: Sesgo geográfico — solo colonias donde Homie opera.

i24 / Scraper

Qué contiene: Listings activos en Inmuebles24.com en tiempo real (Selenium).
Qué mide: Precio de oferta actual.
Fortaleza: Refleja el mercado del día.
Debilidad: Precio de oferta ≠ precio de cierre. El dueño puede estar pidiendo 15% arriba del mercado.

Calculadora Homie

Qué contiene: Modelo ML propio de Homie (endpoint REST v5).
Qué mide: Predicción de precio basada en features del inmueble + amenidades.
Fortaleza: Único modelo que considera gym, elevador, seguridad, antigüedad.
Debilidad: Black box — sin documentación de features ni confidence interval.

Principio de la cascada

Cada fuente tiene múltiples niveles. Los niveles van de mayor a menor especificidad: el primer nivel busca la colonia exacta + recámaras exactas + m² en rango. Si no hay datos, el siguiente nivel relaja uno o varios filtros. El proceso para en el primer nivel que produce al menos 1 resultado.

✓
Diseño correcto: P1 con n=1 es mejor que P6 con n=20

Si el primer nivel devuelve una sola observación, esa observación es el match más preciso posible: misma colonia, mismas recámaras, m² en rango, últimos 12 meses. Un fallback P6 con 20 observaciones mezcla colonias adyacentes con mercados distintos, ventanas temporales amplias y recámaras diferentes ajustadas matemáticamente. Menor ruido > mayor volumen.

Pre-carga global de datos (el paso más lento y el más importante)

Antes de procesar cualquier fila, el sistema lanza dos queries masivas a Redshift y guarda los resultados completos en variables globales de módulo (_GLOBAL_SQL_DF y _GLOBAL_HOMIE_DF). La razón de este diseño es crítica para el rendimiento: en lugar de hacer una query a Redshift por cada fila × por cada nivel de la cascada (lo que para 10 filas con 7 niveles SQL serían 70 roundtrips lentos), se hace una sola query grande que trae todo el historial con filtros fijos, y después todos los filtros variables (colonia, recámaras, m², fechas) se aplican en Python sobre el DataFrame ya en RAM. Esta carga es lazy y single-shot: si las variables ya están en memoria de una ejecución anterior del proceso, se reutilizan en 0ms.

ℹ
Tiempo estimado de esta etapa

SQL query maestra: ~8–20 segundos (depende de latencia a db.panoply.io). Homie query maestra: ~5–15 segundos. Total primera ejecución: ~15–35 segundos. Si el DataFrame ya está en memoria: 0ms.

SQL — query maestra SQL (filtros fijos)
-- Solo aplica filtros FIJOS. Los filtros variables (colonia, recs, area, fecha)
-- se aplican después en Python sobre el DataFrame ya cargado.
SELECT date_in, url, COALESCE(price_with_maintenance, price) AS precio_final,
       neighborhood, city, covered_area, rooms, parking, colonia,  -- colonia = CASE WHEN regex
       latitude, longitude
FROM webscraping.postgres_rents
WHERE estado = 'CDMX'
  AND precio_final > 2000
  AND precio_final <= 180000
  AND DATEDIFF(month, date_in, CURRENT_DATE) <= 40
-- Después en Python: precio_inflacion = precio_final × (1 + 0.003 × meses)
SQL — query maestra Homie (filtros fijos)
-- Solo rentas activas o cerradas (no canceladas sin contrato)
WHERE rents._status IN ('started', 'finished', 'finished_early')
-- ROW_NUMBER() OVER (PARTITION BY id_inmueble ORDER BY precio_renta DESC)
-- Toma solo la renta de precio más alto por inmueble (la más reciente relevante)

Ejecución de las 4 fuentes (secuencial, no paralela)

Las 4 fuentes se ejecutan una tras otra, no en paralelo. Antes de lanzar las cascadas, setea la colonia del input en la variable global _CURRENT_COLONIA_INPUT para que las funciones de resolución de CP la puedan usar como sugerencia.

Ejecución secuencial
# 1. Setear contexto de colonia para funciones de resolución de CP
_CURRENT_COLONIA_INPUT = colonia_input   # ⚠ Variable global mutable

# 2. Cascada SQL (7 niveles, Redshift scraping)
(mediana_sql, muestra_sql, nivel_sql) = _process_cascade(SQL_CASCADE, cp, recs, area)

# 3. Cascada Homie (8 niveles, rentas cerradas)
(mediana_homie, muestra_homie, nivel_homie) = _process_cascade(HOMIE_CASCADE, cp, recs, area)

# 4. Scraper i24 (6 niveles, Selenium + Inmuebles24)
(mediana_i24, muestra_i24, nivel_i24) = _scraper_processor(cp, recs, area)

# 5. Calculadora Homie (API ML, sin fallback)
result = calculadora_homie(lat, lon, antiquity, area, recs, bathrooms, parking, has_terrace)
calculadora_prediccion = result.get("original_prediction")

# 6. Limpiar contexto

ℹ
Tiempo estimado por fila

Cascada SQL (filtros en pandas): 0.1–2s. Cascada Homie (filtros en pandas): 0.1–2s. Scraper i24 (Selenium, carga real del browser): 15–45s por nivel activo. Calculadora Homie (API REST): 1–3s. Total por fila: 20–55 segundos. Para 10 filas: ~4–9 minutos.

5

Acumulación de resultados y normalización por edificio

Los resultados de todas las filas se acumulan en una lista de dicts (resultados_por_fila). Solo después de procesar todas las filas del batch se ejecuta la normalización por edificio — esto es necesario porque la normalización necesita ver todas las unidades del mismo edificio juntas para calcular el grupo mayoritario de recámaras y el precio/m² de referencia. Esto significa que si el script se interrumpe a mitad del batch (ej: por un timeout de Selenium o un error de red), los resultados de las filas ya procesadas no quedan escritos en Sheets hasta que termine el batch completo y pase por la normalización. No hay un checkpoint intermedio.

Flujo post-procesamiento
resultados_por_fila = []

for fila in inputs_to_process:
    resultado = { 'mediana_sql': ..., 'edificio_id': ... }
    resultados_por_fila.append(resultado)

# Solo cuando TODAS las filas están procesadas:
resultados_finales = normalizar_por_edificio(resultados_por_fila)

# Ordena por row_num para mantener el orden original
resultados_finales.sort(key=lambda x: x['row_num'])
6

Escritura en Google Sheets (fila por fila)

Itera los resultados normalizados y escribe 10 celdas por fila usando ws.update() con value_input_option='USER_ENTERED'. Los valores None se convierten a '' para no romper la hoja.

⚠
Rate limiting de Google Sheets API

La API de Sheets tiene un límite de ~60 escrituras por minuto. Si el batch tiene más de ~60 filas, la escritura secuencial puede empezar a recibir errores 429. No hay backoff automático implementado.

P7 — Lógica del ajuste N+1

Este nivel asume que no hay datos para N recámaras pero sí para N+1, y re-escala matemáticamente. El proceso completo:

Python — sql_per_bed_plus1_adjusted()
# Paso 1: Buscar con N+1 recámaras (ej: si se quieren 2, busca con 3)
recs_plus1 = recs + 1
df = consulta_sql(colonia, recs_plus1, 0, 1_000_000, historico_meses=36)

# Paso 2: Calcular precio por recámara de la mediana
median_price = mediana(df['precio_inflacion'])
price_per_bed = median_price / recs_plus1   # precio/rec del grupo N+1

# Paso 3: Re-escalar a N recámaras + prima del 11%
adjusted_price = price_per_bed * recs        # precio estimado para N recs
final_price = adjusted_price * (1.0 + 0.11)  # prima: studios valen más/m²

# Ejemplo numérico:
# Input: busco 2 recs en Condesa, no hay datos
# P7 encuentra: 3-recs mediana = $24,000
# price_per_bed = 24,000 / 3 = $8,000/rec
# adjusted = 8,000 × 2 = $16,000
# final = 16,000 × 1.11 = $17,760
❓
Pregunta abierta: ¿por qué una prima del 11% en SQL?

El origen de esta prima no está documentado en el código. La hipótesis más probable es que fue calibrada empíricamente en algún momento comparando medianas de N vs N+1 recámaras para colonias con datos suficientes, y se hardcodeó como constante. Sin embargo, la prima real del mercado puede variar por colonia, por rango de precio y por tipo de inmueble — una prima del 11% puede ser correcta en Condesa pero incorrecta en Vallejo. Acción futura recomendada: calcular esta prima estadísticamente desde el histórico de Homie agrupando por recámaras y calculando el ratio de medianas de precio/m².

Fuente 2 de 4

Cascada Homie — Contratos reales de renta

Es la fuente de mayor calidad porque usa precios de cierre reales, no precios de anuncio. La query maestra de Homie aplica una deduplicación por inmueble vía ROW_NUMBER() OVER (PARTITION BY id_inmueble): si un mismo inmueble tuvo varias rentas, se toma la de precio más alto. El DataFrame resultante contiene una fila por inmueble único.

⚠
Normalización especial de colonias en Homie

La columna colonia en Homie viene en MAYÚSCULAS y sin acentos porque la query de Redshift aplica UPPER(TRANSLATE(neighborhood, 'áéíóúÁÉÍÓÚñÑ', 'aeiouAEIOUnN')). Esto requiere que cualquier colonia que se busque sea pre-procesada con _limpiar_colonia_homie() antes de comparar.

⚠
Diferencia crítica: Homie P1 usa CSV de clúster, SQL P1 usa la librería de CP

Para entender por qué esto importa, hay que ver cómo cada fuente resuelve la colonia:

SQL P1 hace esto: toma el CP del input → consulta la librería postalcodes_mexico → obtiene el nombre oficial de la colonia (ej: "Hipódromo Condesa") → busca en el DataFrame SQL con ese nombre.

Homie P1 hace esto: toma el CP del input → busca en el CSV de clústeres la colonia que ese CP tiene rankeada como #1 por volumen de anuncios → usa ese nombre (ej: puede ser "Condesa" porque tiene más anuncios históricos que "Hipódromo Condesa") → busca en el DataFrame Homie.

El resultado práctico: para la misma propiedad con el mismo CP, SQL puede estar buscando en el vecindario "Hipódromo Condesa" mientras que Homie busca en "Condesa". Son mercados adyacentes pero distintos. Si la mediana de SQL es $18,000 y la de Homie es $21,000, esa diferencia puede no reflejar una diferencia real de precio sino simplemente que cada fuente consultó una colonia diferente. Este es un punto de inconsistencia que puede confundir el diagnóstico cuando se comparan las 4 fuentes entre sí.

Fuente 3 de 4

Cascada i24 — Web scraping en tiempo real

A diferencia de SQL y Homie (datos históricos pre-cargados), i24 realiza un scraping en tiempo real de Inmuebles24.com usando Selenium con undetected-chromedriver. Esto lo hace el más lento (15–45 segundos por nivel) pero el más cercano al precio de mercado del día.

ℹ
Diferencia semántica fundamental

SQL y Homie miden precios de renta cerrados (lo que alguien pagó). i24 mide precios de oferta activos (lo que alguien pide hoy). El precio de oferta está típicamente 10–20% por encima del precio de cierre. Las medianas de i24 y SQL/Homie no son directamente comparables sin aplicar un factor de descuento.

📋 Next step recomendado: hacer un análisis cuantitativo de la diferencia promedio entre los precios i24 y los precios de cierre Homie para la misma colonia/tipo de inmueble/recámaras. Con ese dato, aplicar un factor de descuento calibrado empíricamente (ej: ×0.90 si el descuento promedio es del 10%) a todas las medianas de i24 antes de escribirlas en Sheets.

Flujo interno del scraper — paso a paso

init

Inicialización de ChromeDriver

Detecta la versión de Chrome instalada localmente. Intenta 3 modos en secuencia: (1) versión detectada del sistema, (2) versión extraída del mensaje de error del intento 1, (3) autodetección. Si los 3 fallan, retorna DataFrame vacío — ningún nivel del scraper puede ejecutar.

url

Obtener URL base de la colonia (obtener_url_base_scraper)

Navega a inmuebles24.com/departamentos-en-renta.html, acepta cookies si aparece el banner (timeout 5s), escribe "colonia + delegación" en el buscador, espera 1.5 segundos y hace clic en la primera sugerencia de "Ubicaciones". La URL resultante (ej: /departamentos-en-renta-en-condesa-cuauhtemoc.html) es la URL base de la colonia.

filter

Construir URL filtrada (construir_url_filtrada_scraper)

Añade parámetros de query a la URL base: recámaras y rango de m². El margen de m² aquí es ±15% fijo (no usa la fórmula max(15%, 5m²) de SQL/Homie).

URL resultante (ejemplo)
https://www.inmuebles24.com/departamentos-en-renta-en-condesa.html
  ?operation=2&recamaras=2&sup_min=51&sup_max=69   # para 60m², ±15%
data

Extracción y deduplicación por URL

Scrapa el DOM de la página de resultados de Inmuebles24. Extrae el precio de cada tarjeta de anuncio y la URL única del listing. La deduplicación se hace en memoria via un set urls_vistas: si la misma URL de anuncio ya fue procesada en este run (puede aparecer en múltiples páginas o en múltiples llamadas del scraper), se ignora. Esto evita que el mismo anuncio cuente doble en la muestra. El precio extraído se almacena en la columna precio_ajustado. Diferencia importante: i24 no aplica ajuste de inflación — el precio es nominal del momento del scraping. Esto contrasta con SQL y Homie, donde precio_inflacion es el precio ajustado a pesos de hoy. Comparar la mediana de i24 directamente con la de SQL/Homie sin considerar este detalle puede introducir sesgos adicionales además del ya conocido sesgo de precio-oferta-vs-cierre.

Componente transversal

Resolución de colonias

Este es el componente más complejo y con más puntos de falla del sistema. Su función es transformar un código postal (y opcionalmente un nombre de colonia en texto libre) en un nombre de colonia canónico que pueda usarse para filtrar los DataFrames de SQL y Homie.

El sistema tiene 3 capas distintas de normalización, cada una con su propia lógica de fuzzy matching. Las 3 capas operan en serie — la salida de una alimenta a la siguiente.

Capa 1 — Conversión CP → Colonia (postalcodes_mexico)

La función _resolve_colonia_from_cp_lib(cp) usa la librería postalcodes_mexico para convertir un CP en uno o varios nombres de colonia. Un CP de 5 dígitos puede corresponder a múltiples colonias (ej: el CP 06600 puede cubrir "Juárez", "Hipódromo" y "Roma Norte").

El algoritmo de Jaccard para fuzzy matching de colonias

Cuando hay ambigüedad (varios candidatos para un CP), el sistema elige el candidato más parecido al nombre que el usuario escribió. El algoritmo funciona así:

Python — _find_best_match_colonia()
# Paso 1: Normalizar el input del usuario
# "Hipódromo Condesa" → "HIPODROMO CONDESA" → {"HIPODROMO", "CONDESA"}
colonia_input_words = set(_normalizar_local(colonia_input).upper().split())

# Para cada candidato del CP (ej: ["Juárez", "Hipódromo", "Roma Norte"]):
for candidato in candidatos:
    colonia_words = set(_normalizar_local(candidato).upper().split())

    # Jaccard: palabras en común / palabras únicas totales
    # Ejemplo: {"HIPODROMO","CONDESA"} vs {"HIPODROMO"} = 1/2 = 0.5
    palabras_comunes = colonia_input_words.intersection(colonia_words)
    palabras_totales = colonia_input_words.union(colonia_words)
    score = len(palabras_comunes) / len(palabras_totales)

    # Bonus si el input está contenido dentro del candidato
    # {"HIPODROMO"}.issubset({"HIPODROMO","CONDESA"}) → True → score += 0.3
    if colonia_input_words.issubset(colonia_words): score += 0.3

    # Caso perfecto: match exacto normalizado
    if colonia_norm == colonia_input_norm: score = 1.0
⚠
Problema conocido: sensibilidad a acentos en Jaccard

La función _normalizar_local() sí quita acentos. Pero si el input llega con acentos y el candidato no los tiene (o viceversa), el score puede ser bajo por tokens que no matchean. Ejemplo: "Nápoles" vs "NAPOLES" — si el normalizar no se aplica consistentemente en todos los caminos, estos se ven como palabras distintas. La función sí aplica unicodedata.normalize, pero la inconsistencia puede aparecer en los caminos de fallback que usan _normalizar_local distinto a normalizar.

Capa 2 — Normalización especial para Homie (_limpiar_colonia_homie)

La colonia resuelta en Capa 1 pasa por un segundo proceso antes de buscar en el DataFrame de Homie. Esto es necesario porque el campo colonia en Homie fue normalizado en SQL de forma específica: MAYÚSCULAS + sin acentos + sin prefijos.

_limpiar_colonia_homie() — transformaciones aplicadas
# 1. MAYÚSCULAS + quitar acentos (unicodedata NFKD → ASCII)
"Col. Condesa" → "COL. CONDESA" → "COL. CONDESA"

# 2. Quitar prefijos comunes
prefijos = ['COLONIA ', 'COL. ', 'COL ', 'BARRIO ', 'FRACC. ',
            'FRACCIONAMIENTO ', 'UNIDAD ', 'U.H. ', 'UH ',
            'AMP. ', 'AMPLIACION ', 'EX. ', 'EX-']
"COL. CONDESA" → "CONDESA"

# 3. Normalizar abreviaciones de sección
"NARVARTE 1A. SECC." → "NARVARTE 1A SECCION"
"PORTALES II SECCION" → "PORTALES 2A SECCION"

# 4. Quitar puntuación al final y normalizar espacios múltiples
"NONOALCO:" → "NONOALCO"

Después de limpiar, el sistema intenta matching en dos pasos: 1) coincidencia exacta del string limpio → si no hay resultados → 2) substring matching (str.contains()). El contains puede traer falsos positivos: buscar "CONDESA" puede capturar tanto "CONDESA" como "HIPÓDROMO CONDESA".

Capa 3 — Normalización en SQL (REGEX en Redshift)

La query maestra de SQL pre-normaliza el campo neighborhood crudo del scraping usando una cascada de ~300 CASE WHEN REGEXP_COUNT(). Esta normalización es determinística y corre una sola vez en Redshift cuando se carga el DataFrame global.

SQL — fragmento de la normalización de colonias
CASE
  -- Captura variantes: "Condesa", "condesa", "CONDESA", "Col. Condesa", etc.
  WHEN estado='CDMX' AND REGEXP_COUNT(TRIM(neighborhood),'(C|c)onde(s|z)a|CONDESA')>0
    THEN 'Condesa'
  -- Distingue Hipódromo de Hipódromo Condesa (solo "hipódromo" sin condesa)
  WHEN estado='CDMX' AND REGEXP_COUNT(TRIM(neighborhood),'(H|h)ip(ó|o)dromo|HIPODROMO')>0
    THEN 'Hipódromo'
  -- Roma Norte vs Roma Sur vs Roma (genérico)
  WHEN ... REGEXP_COUNT(neighborhood,'ROMA')>0 AND REGEXP_COUNT(neighborhood,'NORTE|NTE')>0
    THEN 'Roma Norte'
  -- ... ~300 colonias más ...
  ELSE neighborhood  -- ← texto crudo si no coincide ningún patrón
END AS colonia
⛔
Fallo silencioso: colonias sin cobertura en el CASE WHEN

Cualquier colonia que no esté en los ~300 patrones hardcodeados cae al ELSE neighborhood end y queda con el texto crudo del scraping (ej: "Col. Ped. del Pedregal", "LOMAS DE CHAPULTEPEC V SECC"). Cuando Python intenta buscar esa cadena sucia en el DataFrame, probablemente no encuentra nada y la cascada falla desde P1. No hay ningún log que indique "colonia X no está en el catálogo SQL". Esto es invisible en producción.

Post-procesamiento

Normalización por edificio

Cuando se procesan múltiples unidades del mismo edificio (mismo edificio_id), los precios calculados de forma independiente por la cascada pueden ser inconsistentes entre sí — una unidad de 2 recs puede salir más cara que una de 3 recs del mismo edificio. La normalización resuelve esto usando el precio/m² del tipo de unidad más común como referencia interna.

Paso 1 — Identificar el grupo mayoritario de recámaras

Para cada edificio, cuenta cuántas unidades tienen cada número de recámaras. El grupo más frecuente se convierte en el "ancla de precios".

Ejemplo
# Edificio "Sepia Condesa" con 11 unidades:
grupos = {2: 7, 1: 3, 3: 1}  # recs: count
grupo_mayoritario = 2  # ← 7 unidades de 2 recs son el ancla
unidades_ref = [las 7 unidades de 2 recs]

Paso 1B — Subtipo por baños

Dentro del grupo mayoritario, también identifica el número de baños más frecuente. Si todas las unidades del grupo mayoritario tienen 2 baños, las que tienen 1 baño quedan fuera del cálculo de referencia.

Paso 2 — Calcular precio/m² base

Usando solo las unidades del grupo mayoritario (con prioridad Homie > SQL > i24), calcula la mediana del ratio precio/m²:

precio_m2_base = median( mediana_fuente_i / area_i ) para cada unidad i del grupo mayoritario

precio_por_recamara_base = precio_m2_base / grupo_mayoritario_recs

Paso 3 — Re-escalar todas las unidades

Cada unidad del edificio recibe un precio normalizado calculado desde el ancla de referencia. Las primas se aplican cuando una unidad tiene menos recámaras que el grupo mayoritario:

Si el mercado real tiene una prima distinta (o si varía por colonia, por antigüedad del edificio, o por rango de precio), todas las estimaciones de units en minoría quedan sistemáticamente sesgadas. Son candidatas a ser las primeras variables a calibrar empíricamente.

Matemáticas del modelo

Todas las fórmulas y cálculos explicados

1. Ajuste por inflación

Todos los precios históricos se ajustan a pesos del día de hoy usando una tasa mensual fija del 0.3% (≈ 3.6% anual). La tasa se aplica de forma compuesta simple (no interés compuesto verdadero).

precio_inflacion = precio_final × (1 + 0.003 × meses_transcurridos)

meses_transcurridos = (año_hoy - año_date_in) × 12 + (mes_hoy - mes_date_in)
Precio originalHace (meses)FactorPrecio ajustadoDiferencia

⚠
Problema con la tasa fija del 0.3% mensual

La inflación real del mercado de rentas en CDMX ha sido altamente variable: ~3–4% anual en 2019–2021, ~8–12% anual en 2022–2023. Una tasa fija del 3.6% anual subajusta precios de 2022–2023 (cuando la inflación real fue 2–3× mayor) y sobreajusta precios de periodos más estables. El resultado neto es que precios históricos del periodo inflacionario siguen apareciendo más baratos de lo que deberían, haciendo que la mediana calculada sea menor que el precio real de mercado actual.

2. Filtro de outliers en la query SQL

La query maestra aplica estos filtros de rango de precio:

precio_final > 2,000 MXN (elimina datos basura / pruebas)
precio_final ≤ 180,000 MXN (elimina propiedades de lujo extremo)

Hay también una constante MAX_RENT_PRICE = 200,000 definida en el código Python, pero no se usa activamente como filtro en ningún paso del flujo. El único filtro activo es el de la query SQL (≤ 180,000).

3. Fórmula del margen de m²

margen = max( área_m2 × 0.15, 5.0 )
rango = [ floor(área_m2 − margen), floor(área_m2 + margen) ]

El mínimo de 5m² garantiza que incluso inmuebles muy pequeños (20–33m²) tengan un rango de búsqueda mínimamente útil. Sin este mínimo, un depto de 20m² buscaría en [17, 23] — solo 6m² de banda.

4. Ajuste N+1 recámaras (SQL P7)

price_per_bed = median(precio_inflacion_N+1) / (N+1)
adjusted_price = price_per_bed × N
final_price = adjusted_price × 1.11 ← prima del 11%

5. Ajuste N+1 recámaras (Homie P3)

price_per_bed = median(precio_inflacion_N+1) / (N+1)
adjusted_price = price_per_bed × N
final_price = adjusted_price × 1.48 ← prima del 48%

La diferencia de primas entre SQL (11%) y Homie (48%) sugiere que provienen de calibraciones distintas o momentos distintos. No hay evidencia en el código de cómo se calcularon.

6. Deduplicación en _df_processor

muestra = len(df_dedup)

⛔
Bug conocido: drop_duplicates() sin subset de ID

El propio código tiene un comentario marcado como # ¡¡CRÍTICO!!. Al comparar todas las columnas, dos rentas del mismo inmueble con el mismo precio se colapsan correctamente. Pero dos rentas del mismo inmueble con precios distintos (ej: renovación con incremento) cuentan como 2 observaciones separadas, inflando la muestra y sesgando la mediana. La corrección sería df.drop_duplicates(subset=['url']) o el equivalente con el ID de anuncio.

Diagnóstico técnico

Por qué el modelo se desvía — hipótesis y mejoras

Las siguientes hipótesis están ordenadas de mayor a menor impacto estimado en la precisión del modelo, con estimados de tiempo de implementación para cada una.

H1
Primas hardcodeadas (0.48 y 0.11) sin calibración empírica
Las primas aplicadas en la normalización por edificio son el punto de mayor riesgo del modelo. Si el mercado real de CDMX tiene una prima diferente entre studios (1 rec) y departamentos estándar (2 recs), cada edificio procesado con mix de unidades queda con precios sistemáticamente desviados. No hay log que indique cuántas filas son afectadas por esta normalización.
impacto: muy alto afecta: edificios con mix solución: calcular prima desde datos Homie agrupando por recs esfuerzo estimado: 2–4 horas
H2
Sin discriminación de tipo de propiedad — casas, deptos y cuartos mezclados
La query SQL no filtra por property_type. Un cuarto de azotea de 25m² con 1 recámara entra en la misma muestra que un departamento de 50m² con 1 recámara. Esto jala la mediana hacia abajo en colonias donde hay muchas rentas de cuartos baratos. En colonias de mercado premium (Polanco, Lomas), puede no importar. En colonias mixtas (Roma Norte, Doctores) puede sesgarlo significativamente.
impacto: alto afecta: colonias con mercado mixto solución: agregar filtro property_type='apartment' en query esfuerzo estimado: 1–2 horas
H3
Tasa de inflación fija (3.6%/año) vs inflación real del mercado
La tasa de 0.3% mensual es una constante sin calibración dinámica. El mercado de rentas de CDMX tuvo inflación de 8–12% anual en 2022–2023 y ha estado en 5–7% anual en 2024–2025. Precios scrapeados en 2022 están siendo subajustados por un factor de hasta 2×. La mediana resultante es menor que el precio real de hoy, haciendo que el modelo sugiera precios por debajo del mercado.
impacto: alto en datos >18 meses afecta: todos los niveles con ventana >12 meses solución: reemplazar tasa fija con índice INPC de rentas por periodo esfuerzo estimado: 1 día
H4
Precios de oferta vs precios de cierre — i24 sesga hacia arriba
i24 mide lo que el dueño pide, no lo que el inquilino paga. La literatura de mercado inmobiliario indica que el descuento de negociación típico en CDMX es del 8–15%. La mediana de i24 puede estar sistemáticamente 10% arriba del precio de cierre real, haciendo que combinada con SQL/Homie infle el precio sugerido final.
impacto: medio-alto afecta: todos los outputs de i24 solución: aplicar factor de descuento configurable (ej: × 0.90) a medianas i24 esfuerzo estimado: 30 minutos
H5
Mezcla de tamaños en fallbacks sin filtro de m² (P2, P3, P5, P6)
Cuando la cascada relaja el filtro de m², un depto de 40m² y uno de 120m² con las mismas recámaras quedan en la misma muestra. La mediana del precio absoluto de ese pool no representa ninguno de los dos. Para un depto de 40m², la mediana con deptos de 120m² estará inflada. La solución correcta no es añadir precio/m² como feature de output sino usarlo internamente como mejor estimador y luego multiplicar por el área del input.
impacto: medio afecta: niveles P2, P3, P5, P6, P7, P8 solución: en niveles sin filtro de m², calcular mediana(precio/m²) × area_input esfuerzo estimado: 3–5 horas
H6
Listings inactivos contaminan la muestra SQL (precio de anuncio, no de cierre)
La query SQL filtra por date_in (cuando el anuncio fue scrapeado), no por si el inmueble se rentó. Un anuncio publicado a $25,000 que lleva 10 meses activo sin rentarse está sobrevalorado y sigue en la muestra. Estos "listings inactivos" sesgan la mediana hacia arriba.
impacto: medio esfuerzo estimado: requiere datos de cierre en webscraping — difícil
H7
Sin amenidades en SQL e i24 — edificios premium y viejos con el mismo precio
La Calculadora Homie pondera gym, elevador, seguridad, terraza, jardín y piscina. SQL e i24 no capturan amenidades. Dos departamentos idénticos en colonia, recámaras y m², uno con gym+elevador+seguridad y otro en un edificio de los 70s sin elevador, producen la misma mediana en SQL/Homie aunque en el mercado real la diferencia puede ser del 15–25%.
impacto: medio en proyectos nuevos afecta: pricing de edificios premium esfuerzo estimado: requiere enriquecer scraping — 1–2 semanas

Mejoras de arquitectura recomendadas

1. Scoring de confianza por fila
Actualmente el output no indica si el precio vino de P1 (match perfecto) o P7 (fallback extremo). Agregar un campo confianza_sql calculado como función de (nivel alcanzado + muestra) permitiría en Sheets marcar en rojo los precios de baja confianza y tomar decisiones informadas. Fórmula sugerida: confianza = max(0, 1 - (nivel - 1) × 0.12) × min(muestra / 5, 1)
impacto: alto en operaciones esfuerzo: 2–3 horas tipo: feature de observabilidad
2. Modelo ML supervisado como fuente adicional (xgboost/lightgbm)
Con los datos históricos de Homie (contratos cerrados con precios reales), se puede entrenar un modelo de regresión supervisada que use como features: colonia (one-hot o embedding), recámaras, m², baños, antigüedad, parking, y coordenadas (lat/lon con clustering geográfico). Un modelo así aprendería el precio de mercado sin necesidad de cascadas — daría una predicción en ~1ms vs los 20–55 segundos actuales. La Calculadora Homie v5 es exactamente esto, pero es externa y cierra la box. Un modelo propio sería interpretable y entrenable con los datos de la empresa.
Stack sugerido: Python + LightGBM + MLflow para tracking de experimentos. Entrenamiento mensual con datos nuevos de Homie. Evaluación con MAE y MAPE separados por colonia.
impacto: muy alto en velocidad y precisión esfuerzo: 2–4 semanas para MVP tipo: reemplazo arquitectural
3. Procesamiento paralelo de fuentes (de 55s a ~15s por fila)
Actualmente las 4 fuentes se ejecutan en serie. Las cascadas SQL y Homie son pandas en memoria (< 2s cada una) y podrían ejecutarse en paralelo con ThreadPoolExecutor. El scraper i24 (Selenium, ~30s) podría ejecutarse en un thread separado. La Calculadora Homie (API, ~2s) también es independiente. El cuello de botella real es i24 — en paralelo con SQL/Homie, el tiempo total por fila bajaría de ~55s a ~35s.
Blocker actual: la variable global _CURRENT_COLONIA_INPUT crearía race conditions. Antes de paralelizar hay que inyectarla como parámetro.
impacto: ~35% reducción en tiempo total esfuerzo: 1 día (requiere refactor de variable global) tipo: optimización de performance
4. Weighting temporal — datos recientes pesan más
En lugar de una mediana simple que pesa igual todos los registros, implementar una mediana ponderada donde registros más recientes tienen mayor peso. Un decay exponencial simple: peso = exp(-0.05 × meses_desde_date_in) daría peso 1.0 a datos de este mes y 0.22 a datos de hace 30 meses. Esto mejoraría la precisión en mercados con tendencia alcista y haría el modelo más reactivo a cambios de mercado recientes.
impacto: medio en datos con ventana >12m esfuerzo: 3–4 horas tipo: mejora estadística
5. Migración del scraper a API oficial / datos alternativos
El scraper con Selenium es frágil: depende de la versión exacta de Chrome, puede romperse con actualizaciones del DOM de Inmuebles24, y es el paso más lento del pipeline. Alternativas más robustas: (a) Usar la API de Inmuebles24 si es accesible, (b) Contratar un proveedor de datos de MLS como Vivanuncios o Propiedades.com con API, (c) Reemplazar con datos del SIC (Sistema de Información Catastral de CDMX) para precios oficiales registrados.
impacto: muy alto en estabilidad esfuerzo: 1–3 semanas según fuente tipo: mejora de infraestructura
6. Monitoreo de drift y alertas automáticas
No hay ningún sistema que detecte cuando el modelo empieza a divergir del mercado real. Propuesta: una vez al mes, tomar un sample de inmuebles donde el precio sugerido ya se conoce (contratos cerrados en Homie del mes siguiente) y calcular el MAPE (Mean Absolute Percentage Error) real del modelo. Si el MAPE sube más del 15%, disparar una alerta por Slack/email. Esto convierte la herramienta en un sistema auto-evaluado.
impacto: crítico para confianza a largo plazo esfuerzo: 1 semana tipo: observabilidad y MLOps

Análisis de puntos ciegos (cajas negras)

Son las partes del sistema donde la lógica es opaca, los errores son silenciosos, o las decisiones no tienen respaldo documental. Estas áreas son las de mayor riesgo cuando algo falla en producción porque no hay señales visibles de que algo está mal.

⛔
drop_duplicates() sin subset de ID — marcado como CRÍTICO en el propio código

En _df_processor, la deduplicación se hace con df.drop_duplicates() sin especificar subset=['url'] ni ningún identificador único. Esto compara todas las columnas a la vez. El resultado: dos rentas del mismo inmueble con el mismo precio se colapsan correctamente en una sola fila — hasta ahí bien. Pero si un mismo inmueble tuvo dos contratos con precios distintos (por ejemplo, una renovación con incremento de $18,000 a $21,000), ambas filas sobreviven y cuentan como dos observaciones independientes en la muestra, inflando el n y sesgando la mediana. ⛔

El endpoint REST suggestedprice-v5 es un modelo ML externo. No hay documentación en el código de qué features usa internamente, cuál es el rango de entrenamiento, cómo maneja propiedades fuera de distribución (colonias con pocos datos, inmuebles muy grandes o muy pequeños), ni qué significa exactamente el campo original_prediction vs otros campos que el endpoint también devuelve. Se usa el valor crudo sin ninguna validación de rango ni confidence interval. Si el modelo de Homie se actualiza o depreca en producción, la herramienta falla silenciosamente devolviendo None en esa columna.

⚠
Query REGEX de colonias en SQL — cobertura sin monitoreo

La query maestra de Redshift tiene ~300 cláusulas CASE WHEN REGEXP_COUNT(neighborhood, '...') que convierten el texto crudo del scraping a nombres canónicos de colonia. Todo lo que no coincide con ningún patrón cae al ELSE neighborhood END y queda con el texto sucio original (ej: "Col. Ped. del Pedregal", "LOMAS DE CHAPULTEPEC V SECC", "Depto en Renta"). Cuando Python intenta buscar esa cadena sucia en el DataFrame, no encuentra nada y la cascada falla desde P1 sin ningún log ni alerta. No hay ninguna métrica de "% de registros que cayeron al ELSE", ni ningún reporte de "colonias sin cobertura". Esto es completamente invisible en producción — puedes tener una colonia entera sin datos aparentes cuando en realidad los datos existen pero con otro nombre.

⚠
_CURRENT_COLONIA_INPUT — variable global mutable como canal de comunicación

La colonia del input se pasa entre funciones a través de una variable global de módulo, no como argumento explícito. Esto crea un acoplamiento oculto: cualquier función que necesite la colonia del input actual la lee de esta variable global en lugar de recibirla como parámetro. En la ejecución actual (secuencial, una fila a la vez) esto funciona. Pero es el tipo de patrón que explota en cuanto se intente paralelizar el procesamiento con ThreadPoolExecutor o similar, porque dos threads podrían estar escribiendo y leyendo la variable al mismo tiempo con valores de filas distintas — un race condition garantizado. También dificulta el testing unitario de las funciones de resolución de colonia.

⚠
Primas hardcodeadas (0.48 y 0.11) — origen desconocido

Las primas aplicadas en la normalización por edificio cuando una unidad tiene menos recámaras que el grupo mayoritario (Homie ×1.48, SQL ×1.11) están definidas como constantes en el código sin ningún comentario que explique cómo se calcularon, en qué fecha, con qué datos, o para qué rango de colonias son válidas. La hipótesis más probable es que fueron calibradas empíricamente en algún momento y se hardcodearon. El riesgo: si el mercado real tiene una prima diferente (o si la prima varía por colonia, tipo de inmueble o rango de precio), todos los edificios con mix de tipos de unidad quedan con precios sistemáticamente sesgados en la misma dirección, sin ninguna señal de que esto está ocurriendo.

⚠
MAX_RENT_PRICE = 200,000 — constante declarada pero nunca usada

Existe una constante MAX_RENT_PRICE = 200,000 definida en el módulo Python, pero una búsqueda en el código confirma que no se aplica como filtro activo en ningún paso del flujo de procesamiento. El único límite superior de precio efectivo es el de la query SQL maestra (precio_final <= 180,000). La presencia de esta constante sin uso puede generar confusión: alguien que lea el código puede asumir que existe un filtro de $200,000 cuando en realidad no opera.

⚠
Código muerto post-return en homie_recs_only_100m_cp_library

En la función homie_recs_only_100m_cp_library, alrededor de las líneas 1531–1548, hay un bloque de código con asignaciones de colonia y cálculos de área que se encuentra después de un return. No afecta el funcionamiento del sistema, pero genera ruido cognitivo para cualquiera que lea o mantenga el código, y puede llevar a errores si alguien intenta modificar esa función asumiendo que ese bloque sí se ejecuta.
